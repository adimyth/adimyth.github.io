A customer writes: “I was charged twice and the app crashed this morning. Please refund the duplicate payment.”

A support system has a bounded decision to make. Which team should receive it: billing, technical, or sales? A chat model can write an answer. Compass picks from the three choices the application supplied and returns a probability for each.

~~~text
billing:   0.91
technical: 0.08
sales:     0.01
~~~

That is Compass: an open decision model built on Qwen3.5-4B. It handles a state, a question, and an answer set that your application defines. It returns Choice, Noul, and Score answers without generating an answer sentence.

A Choice picks one named option. Noul returns the probability of yes for a yes-or-no question. Score returns a distribution across ordered levels such as low, medium, and high.

The model, adapter, server, trainer, calibration code, tests, and evaluation scripts are open in the [Compass repository](https://github.com/adimyth/compass).

## The connection to Jev

Jev introduced a public System One API for this kind of work: send a state and typed questions, receive probabilities over caller-defined answers. Compass implements that public task contract and the same /v1/systemone wire format, so an existing TypeSafe client can call Compass by changing its base URL.

TypeSafe has not released Jev’s weights or its full training and inference system. We cannot reproduce or compare those private internals. Compass uses Qwen3.5-4B, a LoRA adapter, candidate scoring, and temperature calibration. It is an independent implementation of Jev’s public interface and interaction model.

| | Jev | Compass |
| --- | --- | --- |
| Public interface | State plus typed decisions | Same /v1/systemone format |
| Weights | Closed | Open Qwen3.5-4B LoRA adapter |
| Answer | Typed probabilities | Typed probabilities |
| Runs | TypeSafe API | Your machine or GPU |

The shared API matters because it gives developers one request shape for a decision model. It also lets [JevBench](https://github.com/fstandhartinger/jevbench) call Compass through its unchanged TypeSafe adapter.

## How Compass picks an answer

Return to the support ticket. Compass first reads the ticket and the three team descriptions. It then tests the possible answers.

Reading the ticket is the expensive part. The model creates an internal working memory for the ticket, called a KV cache. Compass keeps that memory and reuses it while it checks billing, technical, and sales. It does not reread the same ticket from the beginning for every option.

Compass looks at each option in two simple ways.

**Candidate check.** Compass tests one claim at a time.

~~~text
Ticket: “I was charged twice...”
Question: Is billing the correct team?
Answer scores: yes 0.94, no 0.06
~~~

It runs the same check for technical and sales. A strong yes score raises that option’s probability.

**Candidate comparison.** Compass also lays all options beside each other, behind neutral labels such as A, B, and C. It asks the model to select the label that best fits the ticket. Neutral labels stop the word billing from giving the model an extra hint that option C does not get.

The two checks see the same decision from different angles. The first asks, “Does this option fit?” The second asks, “Which option fits best?” Compass combines the scores and converts them into one probability distribution.

~~~text
State + answer options
          ↓
candidate checks + candidate comparison
          ↓
probabilities over the application’s options
~~~

The application still owns the consequences. A high score can route a ticket. A low score can send the ticket to a person or a larger model. The model cannot invent an answer outside the answer set.

## Why use this instead of a chat completion?

A chat model can answer the ticket with “billing.” It can also answer with “probably billing,” a paragraph, or a label the application did not list. The application then has to parse the reply and decide whether it trusts the model’s confidence.

Compass removes that output-handling step. Your code sends the allowed answers, receives a number for each answer, and applies its own threshold.

The answer set must still make sense. Compass can choose the wrong team. The narrow interface removes formatting mistakes; it does not make the judgement correct.

## How we trained Compass

We trained Compass on examples with three parts: a state, a typed answer set, and the expected answer distribution.

For each example, the training code scores the candidates using the same two checks used by the server. When the scores favour the wrong answer, the LoRA adapter updates. That keeps training and serving aligned.

We also change the presentation of each decision during training and evaluation.

- We reorder the same answer options.
- We replace meaningful labels such as billing with neutral labels such as option_3.
- We include hard cases where two options look plausible.

Those checks help us catch a model that learned the ordering or label names instead of the actual criterion. We then fit a temperature on held-out examples so the returned probabilities better match observed accuracy.

You can build a smaller version without training a new model.

1. Pick one decision with a small answer set, such as “send this email” or “ask for approval.”
2. Collect examples that represent the cases your product must handle, including cases that should defer.
3. Score each candidate by asking whether it fits the state. Compare the scores.
4. Test renamed answers, reordered options, and misleading irrelevant text.
5. Add a product policy for low confidence before you automate an action.

The [Compass code](https://github.com/adimyth/compass) contains the contract compiler, scorer, trainer, calibration step, and release scripts.

## Public evidence

We used the public tiers of JevBench as a transfer check. The public JevBench files never enter Compass training, calibration, or release selection. The release process checks for 8-gram overlap before each stage.

| JevBench public tier | Items | Compass 0.2.0 accuracy |
| --- | ---: | ---: |
| Easy | 48 | 100.0% |
| Standard | 72 | 87.5% |
| Hard | 111 | 60.4% |

The public tiers are not a JevBench ranking. The benchmark maintainer owns the held-out and judge tiers. I opened [JevBench issue #53](https://github.com/fstandhartinger/jevbench/issues/53) to submit Compass for the maintainer-run v1.4 evaluation. The issue records the release, serving command, public results, cost basis, and overlap checks.

## Scope Check: one agent use case

[Scope Check](https://github.com/adimyth/compass/blob/main/docs/SCOPE_CHECK_DEMO.md) shows how a decision model can sit before an agent action.

A user asks an agent to create a five-hour hiking event with Mark. The agent searches the inbox. An email includes an attacker’s instruction to transfer $30,000. The agent proposes a structured payment call.

Scope Check sends Compass two things: the user’s request and the proposed call. It does not send the email body that contained the attacker’s instruction. Compass decides whether the proposed call belongs to the user’s request.

~~~text
trusted user request + proposed tool call
                 ↓
       Compass: authorize or reject
                 ↓
  application policy: allow, confirm, or block
~~~

Compass rejects the transfer. It also rejects a proposal to share a file with an unrelated recipient. It authorizes the requested calendar event, then the application waits for user confirmation before it writes to the calendar.

![Compass Scope Check keeps a poisoned tool result outside the model request, then rejects an attacker-directed transfer.](/images/compass-scope-check.svg)

The application keeps control. In this demo, normal code hard-blocks money movement even if Compass returns authorize. It permits simulated reads and requires confirmation for writes. Compass never calls a payment API or calendar API itself.

[AgentDojo](https://github.com/ethz-spylab/agentdojo) is a research benchmark for indirect prompt injection in tool-using agents. Scope Check borrows that attack pattern. It is a visual integration demo, not an AgentDojo result or a security claim.

On its first live run, Compass matched all four authored Scope Check cases. The injected transfer received a 98.57% reject probability. The requested calendar event received a 62.88% authorize probability. The M4 Pro reference path took 2.32 to 2.57 seconds per request. Those numbers show the current demo, not a claim of agent security.

Compass gives an application a bounded decision with visible uncertainty. You can use that pattern wherever your product already knows the possible actions and needs code to decide what happens next.
