A trained model's weights sit in memory as fp16 or bf16 numbers, two bytes each. An 8B parameter model is 8 billion of those numbers, roughly 15GB, and every one of them has to move through the chip to produce a single token. Moving that 15GB from memory to the compute units and back, once per token, is where the time goes. The arithmetic on top of it is cheap by comparison.

**Quantization shrinks those numbers after training is already done.** Round each weight down to fewer bits, 8, 5, 4, and there's less to move. A checkpoint a third of the size moves a third of the data per token, which is most of why a quantized model generates faster. It also gets worse at its job, and how much worse comes down to how you round.

Six methods round differently, and this essay works through what each one actually does: round-to-nearest, GGUF's k-quants, Apple's MLX, HQQ, AWQ and GPTQ. They split cleanly in two. The first four decide how to round by looking only at the weight values. The last two push real text through the model first and use what they see, and they are the reason this essay needed a second machine. All six quantize the same model, **Llama 3.1 8B Instruct**, and every number below sits against that model unquantized. Quality comes from two numbers, perplexity over the wikitext-2 test split and accuracy on a fixed 50-question MMLU subset that every checkpoint sees identically.

The aim is to explain each method on its own terms and report what it costs, not to rank them against one another. Some comparisons here are sound and the essay makes them plainly. Within the k-quant family one tool quantizes one file at three bit widths, so the ordering means what it appears to mean. Others are not sound, because group size, the quantization library and the measuring tool can all change at once between two methods, and where that happens the essay says so instead of ranking them anyway.

## Post-training, not quantization-aware

Two families get grouped under "quantization" and they are not the same kind of thing.

**Post-training quantization (PTQ)** takes a finished model and rounds its weights. No gradients, no backward pass, no retraining. Some methods use a small calibration set to decide *how* to round more carefully; none of them touch the model's actual training.

**Quantization-aware training (QAT)** puts fake-quantization operations into the forward pass during training or fine-tuning, so the model's own weights adapt around the rounding error. It needs the training pipeline and a real training run.

Everything in this essay is post-training.

## The shared starting point

Every result below is measured against one baseline: **Llama 3.1 8B Instruct in fp16**, unquantized. Its measurements on the M4 Pro are:

| Metric | Llama 3.1 8B, fp16 |
| --- | --- |
| Size on disk | 14.97 GB |
| Generation (tg128) | 15.5 t/s |
| Prompt processing (pp512) | 315.5 t/s |
| Perplexity, wikitext-2 | 7.395 \* |
| MMLU, 50q subset | 82.0% (41/50) |

\* Measured a second way as well, giving 7.365. Two tools are needed because neither reads every format, and the last section of this essay covers what separates them.

RTN and the k-quants below need that model in GGUF format first; MLX and HQQ quantize straight from the HF checkpoint instead. llama.cpp ships a conversion script, `convert_hf_to_gguf.py`, that reads the checkpoint and writes an **unquantized f16 GGUF**, no rounding yet, just a format change. For this Llama 3.1 8B baseline, that's a 14.97GB file and takes about 40 seconds.

RTN and the k-quants all start from that one file, built once and quantized four separate ways.

## RTN: round to nearest, and nothing else

Split the weights into blocks of 32. Each block gets one shared **scale**, a single number, call it `d`. Every weight in the block gets replaced by two things: `d` (stored once, shared by all 32) and a small integer **code**, stored per weight in 4 bits. To read a weight back later, multiply: `weight ≈ code × d`.

`d` is set from the block's own largest weight, so nothing in the block overflows what 4 bits can hold. A 4-bit signed code can be any whole number from -8 to 7, so `d = max(abs(weights)) / 8`.

This is a deliberately simplified RTN illustration, not a literal transcription of llama.cpp's `Q4_0` encoding. The benchmark command below uses `Q4_0`, whose signed scale and packed-code convention differs slightly, but it follows the same scale, round-to-nearest, and reconstruct sequence.

**A block of four, to see the mechanism** (real blocks hold 32; four keeps the table small):

| Weight | `weight / d` | Code (rounded) | Dequantized (`code × d`) |
| --- | --- | --- | --- |
| 0.90 | 6.00 | 6 | 0.90 |
| -1.20 | -8.00 | -8 | -1.20 |
| 0.30 | 2.00 | 2 | 0.30 |
| -0.05 | -0.33 | 0 | 0.00 |

`d = 1.20 / 8 = 0.15`, set by the largest weight, -1.20. The three larger weights come back almost exactly. The smallest one, -0.05, rounds to code 0 and vanishes.

**RTN's error is a flat ±d/2, the same for every weight in the block, whether that weight started out big or tiny.** A quiet, near-zero weight and a loud one both get rounded to the nearest multiple of 0.15 here, so the quiet one loses a much bigger fraction of itself.

```bash
llama-quantize model-f16.gguf model-q4_0.gguf Q4_0
```

Quantizing the 8B model took **9 seconds**.

| Metric | fp16 | RTN `Q4_0` |
| --- | --- | --- |
| Size on disk | 14.97 GB | 4.34 GB |
| Generation (tg128) | 15.5 t/s | 48.5 t/s |
| Prompt processing (pp512) | 315.5 t/s | 377.8 t/s |
| Perplexity, wikitext-2 | 7.395 | 7.804 (+5.5%) |
| MMLU, 50q subset | 82.0% (41/50) | 76.0% (38/50) |

RTN shrinks the checkpoint by 71% and triples decode throughput, for +5.5% perplexity and six points of MMLU. That MMLU drop is 3 questions out of 50 changing from right to wrong, which sits close to the noise floor of a subset that small. Read it as directional, and lean on perplexity for the fine-grained comparisons.

The speed measurements tell a more predictable story. Decode is memory-bandwidth bound: producing one token means moving the entire checkpoint through memory, so a checkpoint a third of the size moves a third of the data. Prompt processing handles many tokens together and reuses each loaded weight across them, making it primarily compute-bound on this hardware. Quantization still helps, 1.2x here, but not nearly as much as it helps decode, 3.1x.

## GGUF k-quants: an offset and scale at the same size

RTN gives every weight in a 32-weight block one shared scale. That's the weak spot: the scale has to be sized for the block's largest magnitude, so a quiet weight can get crushed towards zero, the way `-0.05` did above. k-quants keep the same 32-weight grouping, but store an offset alongside the scale, so their 16 codes cover the block's actual minimum-to-maximum range rather than a symmetric range around zero. The challenge is fitting that second number into the same storage budget.

**What "sub-block" means here.** A sub-block is exactly the same size as an RTN block: 32 weights. It's called "sub" because eight of them get bundled together into a bigger container, a **super-block** of 256 weights, covered further down. For now, ignore the super-block and look at what one sub-block does differently from RTN.

**A weight needs two numbers to place it, not one.** RTN reads a weight back as `code × d`, always anchored at zero. k-quants read a weight back as:

```
weight ≈ code × scale + offset
```

`code` is the same kind of small integer as before, but now unsigned, 0 to 15 (4 bits gives 16 possible codes). `scale` and `offset` are two numbers computed once per sub-block: `offset` is just the sub-block's smallest weight, and `scale` is sized so that code 15, the largest available code, lands exactly on the sub-block's largest weight:

```
scale  = (largest weight − smallest weight) / 15
offset = smallest weight
```

**Two sub-blocks, shown by their endpoints.** Each real sub-block holds 32 weights; the table shows only the smallest and largest, because those are the two values that set its `scale` and `offset`. A is the four-weight example above, shown only at its endpoints. B is another 32-weight stretch of the same weight matrix whose values are much smaller in magnitude, from -0.03 to 0.04:

| | Weight | `scale` | `offset` | Code | Dequantized |
| --- | --- | --- | --- | --- | --- |
| Sub-block A | -1.20 | 0.14 | -1.20 | 0 | -1.20 |
| Sub-block A | 0.90 | 0.14 | -1.20 | 15 | 0.90 |
| Sub-block B | -0.03 | 0.0047 | -0.03 | 0 | -0.03 |
| Sub-block B | 0.04 | 0.0047 | -0.03 | 15 | 0.04 |

Sub-block A's `scale = (0.90 − (−1.20)) / 15 = 0.14`. Sub-block B, computed the same way from its own smallest and largest weight, gets its own much smaller `scale = 0.0047`, sized for numbers a hundred times quieter than A's. `Q4_0` would also give B its own 32-weight block and scale; it would not make B share A's scale. The difference is that RTN uses one symmetric scale around zero, while `Q4_K` stores both a scale and an offset. Here the latter maps B's two endpoints exactly to codes 0 and 15.

**Keeping two numbers without spending more.** `Q4_0` spends one fp16 scale, 16 bits, for every 32 weights. Eight blocks therefore use 128 metadata bits for 256 weights. A `Q4_K` block needs both a scale and an offset, which would naively cost 256 bits.

llama.cpp's fix: group eight sub-blocks into one **super-block of 256 weights**. It compresses each sub-block's scale and offset to 6 bits, for 6 bits × 2 × 8 = 96 bits, then stores two fp16 super-block scales to decode those compressed values, another 32 bits. That is 128 bits in total: exactly the metadata budget `Q4_0` uses for eight ordinary blocks. The weight codes remain 4-bit in both formats, so both work out to 4.5 bits per weight.

This two-level structure is the defining mechanism of the formats llama.cpp calls *k-quants*. The `K` in `Q4_K` is a family label, not a name for the compressed scale and offset; the original implementation does not document an expansion of the letter.

**`_M` is a separate decision: which tensors get more bits.** Not every part of the model loses equally from rounding. `Q4_K_M` quantizes most of the model with the Q4_K scheme above, but bumps two specific tensors, the attention output projection and the FFN "down" projection, up to a chunkier 6-bit scheme (`Q6_K`) for roughly half the model's layers, mostly the ones nearest the start and the end of the network. The exact rule for which layers is fixed in [llama.cpp's quantization source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-quant.cpp), not computed freshly for this specific model. `Q5_K_M` follows the same idea from a 5-bit base.

```bash
llama-quantize model-f16.gguf model-q4_k_m.gguf Q4_K_M
llama-quantize model-f16.gguf model-q5_k_m.gguf Q5_K_M
llama-quantize model-f16.gguf model-q8_0.gguf   Q8_0
```

All three quantize from the same f16 GGUF that RTN used, each pass taking well under a minute.

| Metric | fp16 | `Q4_K_M` | `Q5_K_M` | `Q8_0` |
| --- | --- | --- | --- | --- |
| Size on disk | 14.97 GB | 4.58 GB | 5.34 GB | 7.95 GB |
| Generation (tg128) | 15.5 t/s | 44.9 t/s | 31.2 t/s | 28.1 t/s |
| Prompt processing (pp512) | 315.5 t/s | 359.9 t/s | 329.4 t/s | 362.6 t/s |
| Perplexity, wikitext-2 | 7.395 | 7.622 (+3.1%) | 7.467 (+1.0%) | 7.399 (+0.05%) |
| MMLU, 50q subset | 82.0% (41/50) | 78.0% (39/50) | 80.0% (40/50) | 80.0% (40/50) |

`Q4_K_M` costs almost the same size as RTN's `Q4_0`, 4.58GB against 4.34GB. For that near-identical budget it buys back nearly half of RTN's perplexity gap, 7.622 against 7.804. That comparison is a clean one: the same tool quantized the same f16 file and scored both against the same baseline, so nothing varies except the scheme. It also answers one more MMLU question correctly, which on a 50-question subset is noise rather than evidence. Same bits spent, smarter arithmetic, a real perplexity improvement at no extra size.

`Q5_K_M` sits between `Q4_K_M` and `Q8_0` on size and on perplexity, which is what a 5-bit base type spending more bits than `Q4_K_M` and fewer than `Q8_0` should do. It ties `Q8_0` on MMLU and trails both on prompt processing, neither of which follows from the bit count. At 5.34GB it's a third bigger than `Q4_K_M`, and its perplexity cost drops to +1.0%, a third of `Q4_K_M`'s +3.1%. It's the pick if `Q4_K_M`'s quality cost feels too high but `Q8_0`'s size doesn't feel worth it.

`Q8_0` lands at 7.399 perplexity against fp16's 7.395, close enough to call unquantized. Eight bits per weight barely costs anything, which is why `Q8_0` is the format people reach for when size isn't the binding constraint.

The progression by precision, fp16 < `Q8_0` < `Q5_K_M` < `Q4_K_M`, holds on perplexity in exactly the order you'd expect: more bits, less rounding. `Q5_K_M` and `Q8_0` tie on MMLU at 80.0% despite `Q8_0` being closer on perplexity. Fifty questions is a coarse enough sample that a tie like that is expected, not a sign the two checkpoints are equivalent.

## MLX: built for this hardware, and not automatically cheaper

MLX is Apple's own array framework, unified memory, native Metal. Its default quantization uses the same `weight ≈ code × scale + offset` idea k-quants use, one scale and offset per group of weights, but with a bigger group and no compression on the scale itself.

**The same sub-block A from before, quantized MLX's way.** MLX's default group is 64 weights, twice k-quants' 32. Imagine sub-block A sitting inside a 64-weight group whose other 60 weights happen to span a similar range:

| | Weight | `scale` | `offset` | Code | Dequantized |
| --- | --- | --- | --- | --- | --- |
| MLX group | -1.20 | 0.14 | -1.20 | 0 | -1.20 |
| MLX group | 0.90 | 0.14 | -1.20 | 15 | 0.90 |

That's numerically identical to k-quants' sub-block A, because this group's largest and smallest weight happen to match sub-block A's. The difference shows up when the group isn't uniform. k-quants would give a *second* group of 32, the quiet one, its *own* scale, the way sub-block B got `scale = 0.0047` above. MLX's 64-weight group can't split that finely: one scale covers twice as many weights, so a group straddling both a loud region and a quiet one has to compromise between them, the same problem RTN had, just at half of RTN's resolution.

MLX also stores its scale and offset uncompressed per group, rather than squeezing them to 6 bits the way k-quants do. Its per-group bookkeeping costs *more* than k-quants', not less. **The gap below isn't about how carefully MLX stores its scale.** It's the group size.

```bash
mlx_lm.convert --hf-path <model> --mlx-path out/ -q --q-bits 4 --q-group-size 64
```

| Metric | fp16 | RTN `Q4_0` | MLX 4-bit |
| --- | --- | --- | --- |
| Size on disk | 14.97 GB | 4.34 GB | 4.22 GB |
| Generation (tg128) | 15.5 t/s | 48.5 t/s | 52.8 t/s |
| Prompt processing (pp512) | 315.5 t/s | 377.8 t/s | 359.7 t/s |
| Perplexity, wikitext-2 | 7.365 \* | 7.804 (+5.5%) | 7.949 (+7.9%) |
| MMLU, 50q subset | 82.0% (41/50) | 76.0% (38/50) | 76.0% (38/50) |

\* MLX's perplexity sits against a second fp16 baseline, 7.365 instead of 7.395. The last section of this essay explains why there are two and why the percentages still compare.

MLX comes out a shade smaller than RTN, a shade faster to decode, and about two points worse on perplexity. Both checkpoints go by the name "4-bit." The phrase describes bits per weight and says nothing about the grouping those bits are computed over.

**"4-bit" alone doesn't specify a quantization scheme.** Group size is a second parameter, and most model cards leave it out.

Both land on 76.0% MMLU, the same 38 of 50 questions. Two checkpoints two perplexity points apart can score the same on 50 questions, which is what a subset that small can resolve.

MLX's MMLU pass took **40 seconds**. The GGUF checkpoints' MMLU passes took **25-27 minutes each**. That gap has nothing to do with the models. The GGUF path scores multiple-choice answers by asking a `llama_cpp.server` instance over HTTP, one request per answer choice, four per question. MLX's path calls `lm_eval` directly against the loaded model in the same process, batched, no network round-trip. Same 50 questions, same scoring logic, entirely different plumbing underneath.

## HQQ: a better fit per group

RTN sizes its scale off the largest weight in a block and leaves it there. k-quants and MLX size scale and offset off the block's min and max, which is better, and still reads two numbers off the data: whatever the two most extreme weights happen to be, every other weight in the group has to live with the scale those two dictate. HQQ does neither: for each group it solves a small optimization problem, searching for the scale and zero-point that minimize the total reconstruction error added up across every weight in the group, not just the two at the edges.

**A 16-weight group makes the mechanism visible.** Take two outliers, -1.20 and 0.90, and fourteen ordinary weights clustered around 0.10:

| | Weight | Min/max recon | Min/max error | HQQ recon | HQQ error |
| --- | --- | --- | --- | --- | --- |
| Outlier | -1.20 | -1.20 | 0.000 | -1.16 | +0.040 |
| Cluster | 0.094 | 0.06 | -0.034 | 0.10 | +0.006 |
| Cluster | 0.111 | 0.06 | -0.051 | 0.10 | -0.011 |
| Cluster | 0.117 | 0.06 | -0.057 | 0.10 | -0.017 |
| Cluster | 0.122 | 0.06 | -0.062 | 0.10 | -0.022 |
| Outlier | 0.90 | 0.90 | 0.000 | 0.80 | -0.100 |

Both schemes use the same scale here, dictated by the same two outliers, so both spend a single code on the entire fourteen-weight cluster, the same coarse resolution either way. Min/max keeps that scale anchored so the outliers come back exact, and lands the cluster's one shared code at 0.06. Every cluster weight sits well above that, so every cluster weight comes back too low. HQQ's optimizer doesn't insist on hitting the outliers exactly. It shifts the code grid down, giving up some accuracy on the two rare outliers (-1.16 and 0.80 instead of exact) so the cluster's one shared code lands at 0.10, right where the fourteen ordinary weights sit. Same resolution, better-centered grid: the cluster's errors shrink to roughly a third of min/max's. Summed and squared across all sixteen weights, min/max's total error is 0.023; HQQ's is 0.017, about 25% lower, from the same 4 bits, the same group size, no extra information.

Real weight groups run 32 to 64 wide with outliers scattered more thinly than this toy example, but the trade is the same one: a little more error on the rare extreme weights buys a lot less error on the many ordinary ones. Quantizing one real weight matrix from this model (`down_proj` in layer 10) at 4-bit, group size 64, confirms it at scale: HQQ's optimized scale and offset land 35-40% closer to the original weights than RTN's naive min/max scale, same group size, same bit width, measured as mean squared reconstruction error. Group for group, HQQ is a better fit.

```python
from hqq.models.hf.base import AutoHQQHFModel
from hqq.core.quantize import BaseQuantizeConfig

qcfg = BaseQuantizeConfig(nbits=4, group_size=64)
AutoHQQHFModel.quantize_model(model, quant_config=qcfg, compute_dtype=torch.float16, device="mps")
```

Quantizing the 8B model took **3 minutes**, most of it the closed-form solve running per group across every layer.

| Metric | fp16 | RTN `Q4_0` | HQQ 4-bit |
| --- | --- | --- | --- |
| Size on disk | 14.97 GB | 4.34 GB | 5.61 GB |
| Perplexity, wikitext-2 | 7.365 \* | 7.804 (+5.5%) | 7.815 (+6.1%) |
| MMLU, 50q subset | 82.0% (41/50) | 76.0% (38/50) | 76.0% (38/50) |

\* Same second baseline as MLX, for the same reason. See the last section.

A better per-group fit and a better end-to-end result are two different claims. HQQ reconstructs each weight group closer to the original than RTN does, and still finishes a hair behind it, +6.1% against +5.5%, in a checkpoint 1.3GB larger. Lower error inside one group buys you nothing you can count on once it has to survive 32 layers. The margin sits near the resolution of this comparison, and it does not go HQQ's way.

Generation speed for this checkpoint stays out of the charts below, for a reason that has nothing to do with quantization. HQQ's default backend dequantizes each layer's packed weights on every forward call rather than caching the dequantized tensor, and a single-token decode step does barely any arithmetic to offset that cost, so this checkpoint generated at **0.6 tokens/sec**, roughly 200 times slower than fp16. That per-call dequantization isn't specific to Apple Silicon: it's what the default backend does on any device. HQQ ships faster, fused backends built to avoid it (`torchao_int4`, `marlin`, `bitblas`), but all three are CUDA-only, so a CUDA user has a way around this and a Mac user does not. Plain CUDA on the same default backend would still pay the same per-call cost, just against faster hardware underneath it.

## Everything so far has only looked at the weights

RTN reads a block's largest value. k-quants and MLX read a group's min and max. HQQ solves for the scale and offset that fit a group best. Four methods, four different answers to the same question, and not one of them has any idea what the model actually does with those weights.

A weight that barely participates and a weight that carries most of a layer's output look identical to all four. Both are just numbers in a group.

The next two methods change that. Each pushes a few hundred real text samples through the model before quantizing anything and watches what happens. That text is a **calibration set**, and it is worth being precise about what it is not: there are no gradients, no backward pass, no weight updates. The model is not learning. The calibration set is only used to *observe*, and what gets observed decides how the rounding is done. This is still post-training quantization.

Two ways to use that observation, and they are close to opposites:

**AWQ decides what to protect before it rounds anything.** It measures which input channels carry the largest activations and gives those channels more of the grid's precision up front.

**GPTQ rounds greedily and then repairs.** It quantizes one column at a time, and after each one it adjusts the columns it has not reached yet to compensate for the error it just made.

## AWQ: spend the grid where the activations are

Start with the observation the first four methods cannot make. Take one weight, rounded with an error of +0.030, and put it in two different input channels of the same layer:

| Input channel | Mean abs activation | Weight | 4-bit recon | Weight error | Damage to the layer's output |
| --- | --- | --- | --- | --- | --- |
| Salient | 8.0 | 0.42 | 0.45 | +0.030 | **+0.240** |
| Ordinary | 0.5 | 0.42 | 0.45 | +0.030 | +0.015 |

Identical weights, identical rounding, identical error. Sixteen times the damage. What reaches the next layer is the weight error multiplied by whatever flowed through it, and activation magnitudes across a layer's input channels are not remotely uniform. A small fraction of channels carry far larger activations than the rest.

AWQ finds those channels and **scales them up before rounding**. Multiply a salient channel's weights by some `s` greater than 1, divide that channel's incoming activations by the same `s`, and the layer computes exactly what it did before. What changes is where those weights sit on the grid: larger values, same absolute step size, so the step is a smaller fraction of them. The channel gets finer effective resolution, paid for by the other channels in the group giving up a little of the range.

The rounding itself never changes. AWQ is ordinary round-to-nearest applied to a rescaled matrix. All the intelligence is in choosing `s`, and it is chosen by search: `llmcompressor` tries **20 candidate values per channel group** and keeps whichever minimizes reconstruction error. Those are the `best_error` figures that scroll past during a run.

**What actually got applied**, read from the checkpoint's own `config.json` rather than the documentation:

| | |
| --- | --- |
| Scheme | `W4A16_ASYM`, 4-bit weights, fp16 activations |
| Group size | 128 |
| Zero-point | yes, `symmetric: false` |
| Ignored | `lm_head` |
| Calibration | `ultrachat_200k`, 256 samples, 2048 tokens, seed 42 |
| Search grid | 20 candidates per group, `duo_scaling: true` |

### The mapping that silently does not run

`llmcompressor` ships four scaling rules for Llama, each pairing a layer whose output gets rescaled with the layers that must absorb the change:

| Smooth | Balance |
| --- | --- |
| `input_layernorm` | `q_proj`, `k_proj`, `v_proj` |
| `v_proj` | `o_proj` |
| `post_attention_layernorm` | `gate_proj`, `up_proj` |
| `up_proj` | `down_proj` |

The run logged a warning worth chasing: `32 mappings were skipped due to incompatible shapes`. Thirty-two is exactly the layer count, so one rule fails in every layer. It is the second one, and grouped-query attention is why:

```
v_proj output = kv_heads x head_dim =  8 x 128 = 1024
o_proj input  =    heads x head_dim = 32 x 128 = 4096
```

Llama 3.1 8B has 32 query heads sharing 8 key/value heads, so `v_proj` emits 1024 values where `o_proj` expects 4096. There is no per-channel scale that bridges those shapes, and the rule is dropped. **The attention output projection receives no activation-aware scaling at all**, in any of the 32 layers. AWQ ran here at three quarters of its mapping coverage, and nothing in the output announces it beyond one warning line.

That is worth knowing before reading the result as a verdict on the algorithm. Grouped-query attention is now standard, so this is not an exotic edge case.

Quantizing the 8B model took **14 minutes 22 seconds** on an L40S.

| --- | --- | --- |
| Size on disk | 14.97 GB | 5.35 GB |
| Perplexity, wikitext-2 | 7.365 | 7.792 (+5.8%) |
| MMLU, 50q subset | 82.0% | 78.0% |
| MMLU, 200q subset | 76.5% | 77.0% |

## GPTQ: round it badly, then fix what you can

AWQ prepares the weights so that ordinary rounding does less damage. GPTQ leaves the weights alone and changes the *order and bookkeeping* of the rounding itself.

It works through a weight matrix one column at a time. Quantize a column, measure the error rounding introduced, then push a correction into the columns not yet quantized so they can absorb it. By the time the last column is reached it carries the accumulated debt of every column before it.

**The target is not what you would guess.** Every other method in this essay tries to make each quantized weight close to the original weight. GPTQ does not. It minimizes the error in what the layer *outputs*, and it will happily make an individual weight less accurate to get there.

That works because input channels are correlated. If two channels tend to carry large activations at the same time, then rounding one weight too far down can be paid back by nudging the other one up: whenever the first under-contributes, the second is there to cover it. How much to nudge is exactly:

```
correction to column j  =  (rounding error at column q) x [H-1]qj / [H-1]qq
```

`H` is a **Hessian** estimated over the calibration text, and those ratios are what "how correlated are these two channels" looks like as a number. **This is the only reason GPTQ needs calibration data.** Without it there is no basis for deciding which remaining column can absorb an error and how much of it.

**A three-column illustration**, grid step 0.15, weights `0.37`, `0.22`, `0.50`, with the inverse Hessian saying column 2 can absorb 60% of column 1's error and column 3 the remaining 40%:

| Step | Column | Presented to the quantizer | Rounds to | Error vs presented | Pushed forward |
| --- | --- | --- | --- | --- | --- |
| 1 | `w1` = 0.37 | 0.370 | 0.30 | **-0.070** | `w2` +0.042, `w3` +0.028 |
| 2 | `w2` = 0.22 | 0.22 + 0.042 = **0.262** | 0.30 | +0.038 | `w3` -0.038 |
| 3 | `w3` = 0.50 | 0.50 + 0.028 - 0.038 = **0.490** | 0.45 | -0.040 | nothing left |

Step 1 rounds 0.37 down to 0.30, leaving the layer 0.070 short, and that shortfall is split forward. Step 2 is then handed **0.262 rather than 0.22**, which crosses the midpoint at 0.225 and rounds to 0.30 instead of 0.15. That flip is the whole mechanism: the same weight, a different rounding decision, because of what happened to a different column.

| | `w1` | `w2` | `w3` | Layer output | Output error |
| --- | --- | --- | --- | --- | --- |
| Original | 0.37 | 0.22 | 0.50 | 1.09 | |
| Plain round-to-nearest | 0.30 | 0.15 | 0.45 | 0.90 | **-0.190** |
| GPTQ | 0.30 | **0.30** | 0.45 | 1.05 | **-0.040** |

Note what GPTQ did to the individual weights. Its `w2` is off by +0.080, a **larger** error than plain rounding's -0.070, and its total absolute weight error is 0.200 against plain rounding's 0.190. Every weight is, collectively, slightly further from where it started. The layer's output error is nearly five times smaller.

That is the trade in one line: **GPTQ makes the weights worse on purpose, in a coordinated way, so the errors cancel where it counts.** Three columns and a coarse grid make it visible; a real layer has thousands of columns and the cancellation is statistical rather than this tidy.

**What actually got applied:**

| | |
| --- | --- |
| Scheme | `W4A16`, 4-bit weights, fp16 activations |
| Group size | 128 |
| Zero-point | **no**, `symmetric: true` |
| Block size | 128 |
| Dampening | 0.01 |
| Activation order | `static` |
| Ignored | `lm_head` |
| Calibration | `ultrachat_200k`, 256 samples, 2048 tokens, seed 42 |

Quantizing took **13 minutes 10 seconds**, slightly *faster* than AWQ, which is the opposite of what the per-column Hessian solve sounds like it should cost. GPU utilization told the same story from the other side: AWQ's scale search pinned the card at 100%, GPTQ's solve hovered near 18%, because it is serial work that cannot fill the device.

## AWQ against GPTQ, the one comparison this project can actually make

Everywhere else in this essay, comparing two methods means comparing two libraries, two group sizes and two measurement tools at the same time. Not here. These two were quantized by the same library from the same calibration set built with the same seed, the same 256 samples and the same 2048-token limit, at the same bit width and the same group size, then scored by the same loop against the same baseline on the same GPU in the same session.

| | AWQ | GPTQ |
| --- | --- | --- |
| Perplexity | **7.792** (+5.8%) | 7.959 (+8.1%) |
| MMLU, 200q | 77.0% | 75.0% |
| Size | 5.35 GB | 5.33 GB |
| Quantization time | 14m 22s | 13m 10s |

AWQ wins on perplexity by 2.3 points, and that gap is far outside the resolution of this measurement.

**One thing stops it from being a clean verdict on the algorithms**, and it is visible only in the checkpoints' own configs:

```
AWQ   symmetric = False   (a zero-point per group)
GPTQ  symmetric = True    (no zero-point)
```

AWQ's default scheme stores an offset per group that GPTQ's does not. It carries strictly more information about each group, which is an advantage that has nothing to do with deciding-before versus repairing-after. The two checkpoints land within 0.02 GB of each other, so that extra information is close to free, which makes AWQ's default look like the better-chosen default. But the honest reading of the table is **AWQ as shipped beat GPTQ as shipped**, not that protecting salient channels beats compensating for error.

Both schemes are each method's documented default, so this is exactly the comparison someone reaching for either library would get. It is a useful result and a poor experiment, and those are different things.

## Why these two ran on different hardware

Neither AWQ nor GPTQ has a Metal or MPS path. Not a slow one, none. The four methods above were measured on an M4 Pro; these two required a rented NVIDIA L40S, which raises the obvious question of whether their numbers can sit in the same tables at all.

For quality, yes, and this was worth checking rather than assuming. The same PyTorch loop scoring the same unquantized weights gives:

| Where | Perplexity |
| --- | --- |
| M4 Pro, MPS | 7.3648 |
| L40S, CUDA | 7.3649 |

Four decimal places apart across two vendors' silicon, and MMLU returned 82.0% on both. Perplexity and MMLU measure the checkpoint, not the machine, so AWQ and GPTQ join the quality tables directly.

For speed, no, and the reason is more interesting than the caveat. On the M4 Pro, quantized checkpoints generate roughly **three times faster** than fp16, because decode is memory-bandwidth bound and a 4.3GB checkpoint moves less than a 15GB one. On the L40S, measured against an fp16 control on that same card:

| | Generation | vs fp16 on the same GPU |
| --- | --- | --- |
| fp16 | 38.1 t/s | 1.00x |
| AWQ 4-bit | 33.4 t/s | **0.88x** |
| GPTQ 4-bit | 32.9 t/s | **0.86x** |

**Both quantized checkpoints generate slower than the unquantized one.** The advantage does not shrink, it inverts.

Two things cause it, and neither is about quantization. `compressed-tensors` under plain `transformers` unpacks 4-bit weights to fp16 and then runs an ordinary fp16 matmul, so the arithmetic saved is zero and the unpacking is pure overhead. And an L40S has enough memory bandwidth that single-stream decode is not starved the way it is on a laptop, so there is much less bandwidth saving to collect in the first place. Serving stacks like vLLM ship fused kernels that make 4-bit genuinely faster on this hardware; plain `transformers` is not that, and this essay measured plain `transformers`.

It is the same shape of result as HQQ's 0.6 tokens/sec above: a number describing a backend, not a checkpoint. Tokens per second is a property of a checkpoint, a kernel and a chip together, and moving any of the three moves the number. That is why the generation-speed chart below carries M4 Pro results only, and these two appear as a ratio against a control measured beside them.

The rest trade size for quality at something close to a constant rate.

Two pairs in this project are controlled tightly enough to say something about method rather than setup. **MLX against HQQ**: both 4-bit, both group size 64, both scored by the same PyTorch loop against the same 7.3648 baseline, 1.8 points apart. **AWQ against GPTQ**: same library, same calibration set, same group size, same loop, same GPU, 2.3 points apart, with the caveat that AWQ's default scheme carries a zero-point and GPTQ's does not. Everywhere else, two methods differ in three things at once. `Q4_K_M` makes the point from the other side, costing 4.58GB against RTN's 4.34GB, measured by the same tool, for roughly half the perplexity penalty.

**Generation speed belongs to a kernel and a chip, not to a checkpoint.** On the M4 Pro most quantized checkpoints generate faster than fp16, because decode is memory-bandwidth bound and smaller weights move faster. HQQ is the exception, held back by its backend rather than its weights. On the L40S the whole effect inverts: AWQ and GPTQ generate at 0.88x and 0.86x of fp16 on that same card, because unfused dequantization costs more than the bandwidth it saves on hardware that was never bandwidth-starved. Three checkpoints, three different stories about 4-bit speed, and none of them is a fact about 4-bit.

Evaluation wall time is the same trap one level down. It tracks the tooling built around a format instead of the checkpoint itself: MLX's 40-second MMLU pass against llama.cpp's 25 minutes comes from an HTTP bridge, not from either model.

## What this experiment settles, and what it doesn't

Every chart above invites a ranking, and most of the rankings it invites are not supported. Worth being explicit about which claims the setup can carry.

**It settles these.**

Bit width against quality inside one family. `Q8_0`, `Q5_K_M` and `Q4_K_M` come from one tool quantizing one file and one loop scoring them against one baseline, so their ordering means exactly what it looks like. The same holds for `Q4_K_M` against `Q4_0`.

What each method costs against its own baseline. "MLX 4-bit costs 7.9% perplexity at group size 64" is a measurement, and every method here has one.

Sizes on disk, which are just file sizes and need no interpretation.

That perplexity is not fully specified by naming the dataset, which is the subject of the last section and the most transferable thing here.

**It does not settle these.**

Which 4-bit method rounds best. Group size varies from 32 to 128 across them, the quantization libraries differ, and two different tools produce the fp16 baselines they are quoted against. Those three things move together, so a gap between two methods cannot be attributed to the rounding algorithm. Two pairs are exceptions: MLX against HQQ, and AWQ against GPTQ, and even the second carries a scheme difference worth stating out loud.

Whether calibration is worth it. AWQ and GPTQ are the only calibrated methods here and they finish at opposite ends of the 4-bit band, at different group sizes from everything they would be compared against. This essay describes what each does and what each cost. It cannot tell you that calibration does or does not pay.

**Anything at all resting on MMLU.** This is the strongest caveat in the essay and it is stronger than it was when the work started. Rescoring four checkpoints on 200 questions collapsed an apparent six-point spread into 2.5 points, reversed the ordering, and put two quantized checkpoints above fp16. The 50-question figures reported throughout are a check against catastrophe, nothing more.

Speed across machines, or across backends on one machine. Tokens per second is a property of a checkpoint, a kernel and a chip together, and moving any of the three moves the number, sometimes by enough to reverse its sign.

None of that makes the measurements less useful. It makes them measurements of specific configurations rather than verdicts on algorithms, which is what two machines and nine checkpoints can honestly produce.

The two CUDA folders come with [`setup_cuda.sh`](https://github.com/adimyth/llm-inference-experiments/blob/main/model-quantization/setup_cuda.sh), which builds the environment on any NVIDIA box, and a committed [`requirements-cuda.lock`](https://github.com/adimyth/llm-inference-experiments/blob/main/model-quantization/requirements-cuda.lock) pinning all 113 packages, because `llmcompressor` moves fast enough that an unpinned number stops being reproducible within months.

Four things sit at the root because duplicating them would break the comparison: [`perplexity_core.py`](https://github.com/adimyth/llm-inference-experiments/blob/main/model-quantization/perplexity_core.py) holds the perplexity convention, [`mmlu_tasks.py`](https://github.com/adimyth/llm-inference-experiments/blob/main/model-quantization/mmlu_tasks.py) holds the fixed 50 questions, [`results_io.py`](https://github.com/adimyth/llm-inference-experiments/blob/main/model-quantization/results_io.py) merges each metric into one results file, and [`plot.py`](https://github.com/adimyth/llm-inference-experiments/blob/main/model-quantization/plot.py) draws the charts above.

Three gotchas, if you build this yourself:

- **`lm_eval`'s `gguf` model type needs a server that returns logprobs for echoed text, not just newly generated tokens.** llama.cpp's own `llama-server` doesn't do this. Only `llama_cpp.server`, from the separate `llama-cpp-python[server]` package, does.
- **`lm_eval --limit N` is a plain positional slice, not a random sample.** The same 50 questions apply to every checkpoint, not a fresh sample each run.
- **A folder named after a real package will be imported as one.** This project has method folders called `mlx/` and `hqq/`, and the scripts put the repo root on `sys.path` to import shared helpers. That makes `importlib.util.find_spec("mlx")` succeed on an empty namespace package, `transformers` caches "MLX is installed" at import time, and the first thing to hit its MLX branch dies with `No module named 'mlx.core'`. Ordinary forward passes never reach that branch. `llmcompressor`'s fx tracing does, so AWQ failed on a machine with no MLX anywhere near it. Import `transformers` before the repo root goes on the path, or take the root back off once the helpers are loaded.
- **HQQ's quantization and reload functions default to `device='cuda'`.** On a Mac, that either crashes or reloads onto the wrong device without warning. Pass `device='mps'` explicitly everywhere. This fixes correctness, not the generation speed above: that's a separate backend issue, covered in the HQQ section.

## Two ways to measure perplexity

No single tool reads every format in this essay. `llama-perplexity`, which ships with llama.cpp, handles the GGUF checkpoints: fp16, RTN and the k-quants. It cannot open an MLX or HQQ checkpoint at all, so those go through a windowing loop written for this project.

Running one metric through two implementations only works if the two agree, and agreement is not automatic. "Perplexity on wikitext-2" leaves out a choice that moves the number: which tokens inside each window get scored.

llama.cpp's answer sits in `tools/perplexity/perplexity.cpp`:

```c
const int first = n_ctx/2;
```

With the default 512-token window, `first` is 256. llama.cpp feeds the model all 512 tokens but scores only the last 256 of them. The reason is context. The first token of a window has nothing in front of it, the second has one token, the third has two, and predictions that early are hard for any model whether or not it has been quantized. Counting them inflates perplexity without telling you anything about the weights. Starting at the halfway mark guarantees every scored token has at least 256 tokens of context behind it.

This project's loop now does the same. [`perplexity_core.py`](https://github.com/adimyth/llm-inference-experiments/blob/main/model-quantization/perplexity_core.py) holds the chunking and the second-half rule in one place, and the PyTorch, MLX and HQQ paths supply only their own model loading and loss computation.

The check worth running is both implementations against the same unquantized weights:

| Implementation | fp16 perplexity |
| --- | --- |
| `llama-perplexity`, C++ and Metal | 7.3950 |
| This project's PyTorch loop | 7.3648 |
| This project's MLX loop | 7.3642 |

Three implementations, three frameworks, the same weights. The two llama.cpp and PyTorch figures land 0.4% apart, about what fp16 kernel differences between Metal and MPS come to. The MLX loop agrees with the PyTorch one to **0.007%**.

That third row was the last one added, and it was added because it was missing. MLX is a genuinely separate framework, so `mlx/perplexity.py` has its own model loading and its own loss computation; only the windowing convention is shared. Until an fp16 control ran through it, MLX's quantized number was being compared against a baseline produced by code that had never been checked against it, which is the same structural mistake as the windowing bug below, one level up. It passed. It could have failed, and nothing else in the project would have caught it.

The same loop was also run on both an M4 Pro and an L40S, giving 7.3648 and 7.3649. Perplexity here is a property of the weights, not the machine.

That agreement is what licenses putting a GGUF checkpoint, an MLX checkpoint and a CUDA-quantized checkpoint in the same table, and it is why MLX, HQQ, AWQ and GPTQ are quoted against 7.365 while RTN and the k-quants are quoted against 7.395.

Scoring the whole 512-token window instead of the second half gives **9.460** on those same fp16 weights. Neither number is wrong on its own terms. But a checkpoint measured one way cannot be read against a baseline measured the other, and the gap between the two conventions is larger than the gap between any two quantization methods in this essay.

## The fifty-question mirage

The perplexity bug above was caught by running two implementations and comparing. Here is what happened when the same suspicion was pointed at the other metric.

Every MMLU number in this essay comes from a fixed 50-question subset, chosen so that seven checkpoints could be scored in an evening rather than a week. Fifty questions was always acknowledged as coarse. It turned out to be worse than coarse.

Four checkpoints were rescored on **200 questions**. Because `lm_eval`'s `--limit` is a positional slice with no shuffling, the larger set is a strict superset: the same 50 questions, plus 150 more.

| | 50q | 200q |
| --- | --- | --- |
| fp16 | **82.0%** | 76.5% |
| MLX 4-bit | 76.0% | **77.5%** |
| AWQ 4-bit | 78.0% | 77.0% |
| GPTQ 4-bit | 76.0% | 75.0% |

At 50 questions the story is clean and quotable: fp16 leads by four points, and 4-bit quantization costs four to six points of accuracy. At 200 questions that story does not survive. The four land within 2.5 points of each other, **two quantized checkpoints score above the unquantized model**, and the ordering has almost completely reversed. MLX went from joint last to first.

Because the sets nest, the culprit can be isolated. Splitting out the 150 questions the small run never saw:

| | First 50 | Questions 51 to 200 |
| --- | --- | --- |
| fp16 | 82.0% | **74.7%** |
| MLX 4-bit | 76.0% | **78.0%** |
| AWQ 4-bit | 78.0% | 76.7% |
| GPTQ 4-bit | 76.0% | 74.7% |

**fp16 was not better. It got lucky.** The first five questions per task happened to be ones the unquantized model answered correctly, and on the other 150 it comes last. The apparent cost of quantization was an artifact of which questions got asked.

The sharpest way to put it: **MLX has the worst perplexity of these four, +7.9%, and the best 200-question MMLU.** Take the accuracy table at face value and MLX is the strongest method in this essay. Perplexity, measured over 144K scored tokens instead of 200 questions, says it is the weakest. Only one of those two metrics is resolving anything at this sample size.

The arithmetic was always there to be read. At 50 questions, the 95% interval on an accuracy near 80% is about **±11 points**. Every gap in the original table sat inside it. A two-point difference is one question. At 200 questions the interval narrows to about ±6 points, which is still wide enough that the remaining spread means nothing.

So the honest conclusion is not that quantization is free. Perplexity, measured over 144K scored tokens with an error under 1%, separates these checkpoints cleanly and consistently. It is that **MMLU at this scale cannot detect what perplexity can see plainly**, and a subset small enough to be convenient is small enough to manufacture a result.

The 50-question figures are still reported throughout this essay, because they are what the other checkpoints have. They should be read as a check that nothing is catastrophically broken, and never as a ranking.

Two metrics, two lessons, and the same shape to both. Perplexity needed a second implementation before its numbers meant anything. MMLU needed four times the questions before its numbers stopped meaning something they shouldn't.

## What it comes to

Quantization is not one number. Bits still dominate, and inside one family the ordering is exactly what you would guess: `Q8_0` costs nothing worth counting, `Q5_K_M` about a point, `Q4_K_M` about three. `Q4_K_M` is the one that earns its keep, matching RTN's size for roughly half the perplexity cost, measured by the same tool.

Below that the picture stops being a ranking. Five 4-bit methods, including two that read real text before deciding anything, finish inside a 2.6-point band while differing in group size, library and measurement tool all at once. The two calibrated methods land at opposite ends of it.

What surprised me was not any method. It was how much work it took to make the numbers mean anything. Perplexity needed three implementations agreeing before a cross-format comparison was legitimate, and the windowing convention alone moved the fp16 baseline from 7.36 to 9.46. MMLU needed four times the questions before an apparent six-point cost turned out to be which questions got asked. Generation speed reversed direction between two machines running the same checkpoint.

The methods are the easy part. Most of them are twenty lines of arithmetic you can work through on paper, and this essay does. Measuring them so the answers survive contact with a second implementation is the part that takes the time, and it is the part worth copying.

A different model or a different machine can reorder all of it. Quantize the model you actually run, measure it against the model it came from, and measure it twice.
